# ADR-139: MCP tools found by search instead of listed; a server whose tools change during a run is followed

Status: Accepted (2026-10-29). Owner: "liệu có cơ chế nào mà agenium hỗ trợ chọn tool dựa trên mô tả của agent, ví dụ như
jev?"; "giả sử tôi có 1 mcp cũng dùng jev … jev của mcp đó hết quota, mcp chuyển qua mode thường tức là show hết hơn 100
tool thì lúc đó agenium có handle được case đó … để toolsearch dễ hơn không". Learned from Anthropic's tool search tool
(`platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool`) and Claude Code's `ToolSearch`; written here.
Amends ADR-62 (agents' MCP servers) and ADR-109 (MCP client).

## Context

- Every MCP tool of an agent's servers was listed in every request: its name, description (up to 1,024 characters) and
  schema. 123 tools shaped like real servers' (`agent/mcp/data/many-tools.json`) take about 9,200 tokens a request;
  Anthropic reports about 55,000 for five common servers, and a model's choice degrading past 30–50 tools.
- Anthropic's API defers tools (`defer_loading`) behind a search tool (a regex, or BM25 over the name, description and
  arguments) whose results the API expands outside the cached prefix; Claude Code lists deferred tools by name and
  loads them with `ToolSearch`. Neither exists on the other vendors Agenium drives (DeepSeek, OpenAI, Gemini, OpenCode,
  Codex, Grok, agy), and only Claude Code had it among the CLIs.
- The MCP client ignored server notices. A server's tool list was taken once per connection and kept until the
  connection's settings changed: a server that offers its own tool search over a few tools and falls back to listing
  all of them (its search out of quota) was never seen to change.

## Decision

1. **A run's MCP tools are a catalogue that follows the servers** (`agent/mcp/src/catalog.rs`). The client notes
   `notifications/tools/list_changed` on every transport (stdio, a Streamable HTTP response stream, the legacy SSE
   stream). A server is listed again when it said its tools changed, when its connection was opened again, or — when it
   declares `tools.listChanged`, whose notice may never reach a client without an open event stream — when its list is
   older than 20 seconds; each run starts from the list as it is. A tool the server no longer lists is not called: it
   says the server dropped it and points to `tool_search` (`tool_gone`).
2. **Past a threshold the MCP tools are found, not listed** (`orchestration/orchestrator/src/tool_search/`,
   `[tool_search]` in `config.toml`): with more than `over_tools` (20) tools or more than `over_tokens` (10,000) of
   definitions (`mode = "auto"`; `always`, `never`), a run lists only the `keep_used` (5) MCP tools its agent called
   most with success (`runs::mcp_tools_used`, a call through `call_tool` counted for the tool it called), names the
   others by server in its capabilities (up to 200 names), and gets two tools:
   - `tool_search(query, limit?, server?)`: the tools that do what the agent describes, each with its server, its
     description and its schema; `select:<name>,<name>` names tools exactly. Output marked untrusted.
   - `call_tool(name, arguments)`: runs a tool of the catalogue by its exposed name (or the server's own name when one
     server has it); the arguments, an object or a JSON string, are fitted to the tool's schema (ADR-105), and the
     tool runs as a listed one (cut output, untrusted, read-only tools only in a review or chat).

   The run's tool list never changes, so a provider's prompt-cache prefix holds (ADR-113) on every vendor. A server
   that declares its tools may change gets the pair at any size: the tools it adds are found, not added to the prompt.
3. **Ranking** (`agent/mcp/src/rank.rs`, `tool_search/index.rs`, `tool_search/jev.rs`): words — BM25 over the name
   (twice), description, argument names and descriptions, common words left out and words stemmed — and meaning — the
   memory's local embedding model (`bge-small-en-v1.5`, ADR-47; each tool embedded once per process) — fused by
   reciprocal rank (k = 60). With the judge on (`[tool_search] judge`, default on, fail-open), the 30 best candidates
   are read in one request (the request written once, each question pointing at a tool) and ordered by the probability
   that a tool does what is asked; candidates under 0.15 are dropped when another is above it. Without the judge, out
   of quota or failing, words and meaning rank alone; without the embedding model installed, its hashing stand-in.

## Measured (2026-10-29)

`quality/eval/examples/tool_search_eval.rs`: the 123 tools and 58 requests worded unlike the descriptions ("give the
customer their money back" → `stripe_create_refund`, `agent/mcp/data/many-tools-queries.json`, generated by
`make_many_tools.py`). A search returns 5.

| Ranking | right tool first | in 3 | in 5 | MRR | ms / search (debug build) |
|---|---|---|---|---|---|
| words (BM25) | 30/58 | 42/58 | 47/58 | 0.62 | 4 |
| words + meaning (bge) | 36/58 | 45/58 | 52/58 | 0.71 | ≈ 40 |
| + judge reading 20 candidates | 53/58 | 55/58 | 55/58 | 0.93 | ≈ 330 |
| + judge reading 30 candidates (kept) | **55/58** | **57/58** | **57/58** | **0.97** | ≈ 310 |

The judge's reading costs about 3,200 input tokens a search (about $0.00014). A plain BM25 without the stop words and
stems found a database tool for "notify the team on slack" (matching "the" and "on") and nothing for "throwing errors".
The miss left: "why did the CI build fail on main" shares no word or close meaning with "GitHub Actions workflow runs".

The prompt: 123 listed tools take about 9,200 tokens a request; found by search, about 700 for their names and 350 for
the two tools.

## Verified (2026-10-29)

- Tests: `rank::tests` (common words and endings, fusion); `a_catalogue_follows_a_server_that_changes_its_tools` (the
  many-tools stdio server from 2 tools to 123 after its search's quota, the stale tool refused, a new run starting from
  the new list); `many_mcp_tools_are_found_by_search_and_called` (no MCP tool listed, `tool_search` → `call_tool`, the
  server's own name and arguments as a JSON string, an unknown tool, the same tool list in every request, the used tool
  listed in the next run); `a_server_that_falls_back_to_all_its_tools_mid_run_is_followed` (the owner's case over
  Streamable HTTP, the notice in the failed call's event stream); golden tasks `mcp-search` and `mcp-fallback`
  (opt-in).
- Real agents (`agenium-eval --task mcp-search|mcp-fallback`): the codename exists only in `releases_codename`'s answer.
  DeepSeek v4.1 flash (API), Codex gpt-6-luna and Claude Code Haiku 5.5 each passed both: found the tool with
  `tool_search` and called it with `call_tool`; in `mcp-fallback` each first used the server's own search, got its
  out-of-quota error, and found the tool among the 123 listed since. Claude Code loaded Agenium's `tool_search` with its
  own `ToolSearch` and used it.

## Consequences

- An agent bound to many MCP tools pays for the few it uses; a server's change of tools during a run is followed
  without a restart. The judge use `tool_search` appears in the judge's activity.
- Not done: Anthropic's own `defer_loading` with `tool_reference` results (the same catalogue could be sent deferred to
  Claude's API so a found tool is called by its own name); the pair works on every vendor meanwhile.
