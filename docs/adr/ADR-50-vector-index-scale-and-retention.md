# ADR-50: `VectorIndex` (exact + usearch ANN sidecar), 100k switch threshold, reader/WAL concurrency, event-log retention

- **Status:** Accepted (owner requirement 2026-10-23 12:26 Asia/Saigon; threshold 100k approved 2026-10-23 15:46 Asia/Saigon; numbers in `docs/STORE-SCALE.md`). Amends ADR-2 (Memory) and ADR-47 (Embedder trait: dimension is fixed per agent database). Rewritten after the benchmarks: earlier drafts said "expansion_search 96, rerank ×4, threshold 50k" — all superseded below.
- **Date:** 2026-10-23 (Asia/Saigon)

## Context

Per-agent memory must stay interactive for years of use. Measured (Linux 8 cores / macOS M4 Pro VM, 384-d, 200 real queries): sqlite-vec exact scan costs 5 / 3 ms @10k, 56 / 34 ms @100k, 323 / 156 ms @500k, 664 / 334 ms @1M (linear), i.e. the 50 ms interactive budget is crossed at ≈ 90k (Linux) / ≈ 150k (macOS). With 4 readers and a writer the FTS5/BM25 path serialised and the WAL grew without bound until fixed (below).

## Decision

1. **Trait `VectorIndex`** (`knn(query, k) -> Vec<Hit>`, `len`, insert/delete hooks, `kind`) with two implementations:
   - **Exact** — sqlite-vec `vec0` (float32, cosine). Always present, always correct; it is the source of truth and the fallback.
   - **Ann** — `usearch` HNSW in a sidecar `agents/<id>.db.ann` (+ `.ann.json`). Defaults: **f16 storage, connectivity 16, expansion_add 128, expansion_search 128 (256 from 200 000 vectors up, `AnnOptions.scale_ef`), rerank off**.
2. **Automatic switch (`IndexMode::Auto`)**: exact below **`DEFAULT_ANN_THRESHOLD = 100_000`** facts per agent (configurable: `AgentOptions.ann_threshold`); from there an ANN build runs in the background (exact keeps serving) and the active index flips when it is ready. 100k is the portable value: it is where Linux exact hits ≈ 56 ms, and 34 ms on macOS (which would allow ~150k but we do not tune per OS). Measured ANN at 100k: p50 0.34 ms, recall@10 0.9885, sidecar 92 MB, build 6 s. `Exact`/`Ann` can be forced (tests, benchmarks).
3. **Search quality knobs (measured, `STORE-SCALE.md` §2.4):** recall@10 on real embeddings, f16: 0.9885 @100k, 0.969 @500k and 0.941 @1M with ef 128; 0.9875 @500k and 0.974 @1M with ef 256 (+0.2 ms). Hence ef 256 from 200k vectors. M=32/ef_add=256 gives 0.996 @500k at 3× the build time (option, not default). **f16 = f32 in recall** (0.9875 vs 0.9885 @500k). On *structureless* random 384-d vectors HNSW recall is 0.15–0.47 (ef 128–512) for any dtype: this is the macOS 0.56–0.80 observation; real embeddings are clustered and do not behave like that. Exact search remains the fallback and the source of truth.
4. **Rerank rejected as default:** re-scoring ×4 candidates from `fact_vec` added ≈ 0.6 ms (a vec0 point lookup loads a whole 1024-row chunk, ≈ 0.15 ms each) for +1–2 recall points. Kept as `AnnOptions.rerank` (off).
5. **Consistency** (the sidecar is derived data and must never serve wrong results): triggers on `fact_vec` append to an `ann_journal` table *in the same transaction* as the write; the sidecar records `applied_seq`, `count`, `sum(id)`, file length and crc32. On open: verify length+crc → replay the journal from `applied_seq` → verify `(count, sum(id))` against `fact_vec`; any mismatch or load error ⇒ discard and rebuild from `fact_vec` (parallel). A search error at runtime falls back to exact and schedules a rebuild. The sidecar is saved every 20 000 inserts, on `flush` and on close (under a *read* lock, so searches continue during a save); the journal is trimmed on each save. Verified by 20× `kill -9` (0 ANN self-hit misses).
6. **Quantization:** `fact_vec` stays float32. Rejected: sqlite-vec `int8` (recall 0.93→0.87 as N grows, *no* speed-up) and `bit` (recall 0.44–0.48). ANN `i8` (recall 0.83–0.91) is selectable (`AnnOptions.dtype`), not default.
7. **Not adopted:**
   - `hnsw_rs` — builds 5–6× slower and ≈ 3× the RAM of usearch at equal recall (100k: 205 s, 504 MB).
   - `vectorlite` — measured: its HNSW index is **not transactional** (not rolled back with the SQLite transaction), and writes to the virtual table *from a trigger fail yet still mutate the index*; official wheels cover only Linux x64, Windows x64 and macOS arm64. (An earlier draft said only "cannot write from triggers".) Either property breaks the single-transaction journal design.
8. **Concurrency model** (measured, `STORE-SCALE.md` §4): one serialized writer (`BEGIN IMMEDIATE`, busy retry) + a **condvar-queued pool of 4 read connections** (fair; replaces per-connection mutexes that starved the writer for 99 s). Read connections set **`mmap_size = 1 GiB`** (`SqliteOptions.mmap_bytes`) — this removed the FTS5/BM25 reader serialisation (≈ 10× throughput; page-cache size and memstatus were not the cause). `SQLITE_CONFIG_MEMSTATUS` is turned off anyway. **WAL gate:** a passive checkpoint (on the writer connection) runs every maintenance tick; if the WAL exceeds `wal_limit_bytes` (64 MiB) `Db::checkpoint_exclusive` pauses new reads, drains in-flight ones, runs `wal_checkpoint(TRUNCATE)` and resumes. `journal_size_limit` = 64 MB; `wal_autocheckpoint` configurable (default 1000 pages). Result at 100k hybrid with 4 readers + writer: p95 22.6 ms, writer 1 487 facts/s, WAL end 12 MB (before: p95 175 ms, writer 25 facts/s).
9. **Event-log retention** (SQLite): `archive_events(ArchivePolicy)` moves events that are older than 30 days **and** beyond the newest 100 000 into `event-archive/events-<from>-<to>.jsonl.zst` (zstd 3, ≤ 250 000 rows/file, deterministic names, fsync + rename, sha256 in the `event_archive` table); the same transaction inserts the archive row and deletes the events. `counter.event` is never reset, so `seq` stays strictly increasing and gap-free across live+archive; `events_since`, `event_by_seq`, `events_for_ticket` fall through to the archive; `verify_archives()` re-hashes and counts. **Idempotency window:** `intent_id` uniqueness is enforced against live events only; retrying an intent older than the window (≥ 100 000 events and ≥ 30 days) would create a duplicate — far longer than any orchestrator retry horizon (seconds–minutes). Measured: 750k rows → 21 MB in 5.6 s; archived read p50 58 ms.

## Consequences

- C++ toolchain required (usearch). Sidecar ≈ 0.9 GB disk and ≈ 1.3 GB RAM per agent at 1M facts (f16), built in ≈ 85 s (8 threads); a missing/invalid sidecar costs that rebuild on open while exact serves.
- Hybrid search at ≥ 500k facts is bounded by FTS5 BM25 (38 ms @500k, 84 ms @1M, single thread) regardless of ANN — documented limit (`STORE-SCALE.md` §7).
- New corruption classes (sidecar) are handled by detection + rebuild, covered by tests (`tests/agent.rs`: crash replay, corrupt and missing sidecar, auto switch, WAL bound, default threshold; `ann.rs`: ef scaling).
- Retention is a SQLite-only feature (parity gap). macOS has not re-run the post-fix concurrency numbers.
